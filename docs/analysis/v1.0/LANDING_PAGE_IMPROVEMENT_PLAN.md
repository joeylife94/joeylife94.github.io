# Freelance Landing Page Improvement Plan v1

## 1) Current strengths

- The core problem-solution narrative is already clear: `manual work -> structured system`.
- Service boundaries (`included / not included`) are visible enough to help early qualification.
- The proof section already contains concrete project visuals and technical credibility.
- CTA is repeated across hero, nav, and mobile action, so the page already has a basic conversion structure.
- Overall, this is not a weak page. It is closer to a **solid portfolio-introduction page** than a **conversion-optimized sales page**.

---

## 2) Biggest gaps for conversion (priority order)

### P0 — Highest priority for first-round conversion lift

1. **Hero message is still too broad**
   - The page explains capability, but not sharply enough:
     - who this is for
     - what kind of operational problem it solves
     - why this should matter now
   - The first screen should make the positioning more specific:
     - manual operations
     - spreadsheet / Slack / email-driven workflows
     - small internal systems / ops pipelines / backend MVPs

2. **No “engagement model” summary**
   - Visitors cannot quickly understand:
     - typical timeline
     - deliverables format
     - communication style
     - scope handling
   - Add a compact block:
     - `Typical timeline / Deliverables / Communication / Scope policy`

3. **No low-friction lead capture path**
   - Mail-only contact usually lowers conversion, especially on mobile and corporate devices.
   - Add a short intake form.
   - Keep email as a secondary fallback.

4. **No FAQ section for key objections**
   - Visitors likely hesitate on:
     - whether small projects are accepted
     - how communication works
     - what happens after handoff
     - stack flexibility
     - IP / ownership
     - privacy / sensitive data handling
   - Add a short FAQ block with 5–7 items.

5. **Featured proof is visible, but not framed as a trust-building case**
   - The page shows projects, but not yet in a strong:
     - `baseline -> change -> result`
     format.
   - Rewrite at least one flagship proof block into a mini case study.

---

### P1 — Positioning clarity and trust improvement

6. **ICP (ideal client profile) is still too broad**
   - "small teams / startups / operators" is directionally correct, but still wide.
   - Replace it with 3 sharper target profiles, for example:
     - `0–10 person SaaS team with operations bottlenecks`
     - `founder validating an internal workflow MVP in 2–4 weeks`
     - `team replacing spreadsheet-based approval / tracking flows`

7. **Outcome metrics exist, but lack context**
   - Metrics like `~30%` and `100 -> 2,000+` are useful, but need framing.
   - Add short proof context for each:
     - baseline situation
     - action taken
     - measurable result

8. **No clear “why now” trigger**
   - Add urgency copy near the hero CTA.
   - Example direction:
     - `If weekly operations still depend on manual QA, reconciliation, copying, or repeated checks, you are likely already paying for it in delivery speed and error rate.`

9. **Package framing can be clearer**
   - Package labels reduce cognitive load and help qualification.
   - Recommended package structure:
     - `Internal Tool Starter`
     - `Workflow Automation Sprint`
     - `Backend MVP Sprint`
   - Show:
     - typical duration
     - expected deliverables
     - best-fit situation

10. **No explicit written proof lines under project cards**
   - Screenshots help, but written trust framing should also be added.
   - Each proof card should include:
     - challenge
     - what was built
     - impact

---

### P2 — Later-stage optimization (not first priority)

11. **No explicit risk-reduction policy**
   - This is useful, but not more urgent than hero / form / FAQ / engagement model.
   - Add later as a compact section:
     - scope freeze checkpoint
     - change-request handling
     - post-handoff bug-fix window

12. **No analytics instrumentation for funnel steps**
   - Add event tracking after core copy / structure changes are done.
   - Recommended events:
     - hero CTA click
     - package CTA click
     - proof interaction
     - form open
     - form submit
     - email click

13. **No SEO structured data**
   - Good to have, but not urgent at this stage.
   - Add later:
     - `Person`
     - `ProfessionalService`
     - `FAQPage`

14. **A/B testing is premature**
   - Do not prioritize headline or CTA A/B tests before:
     - hero sharpening
     - form addition
     - FAQ
     - engagement model
     - featured case rewrite
   - First improve the page structurally, then test.

## 3) Strategic positioning for this page

### Core positioning to strengthen

This landing page should not feel like a generic developer portfolio.

It should clearly position the service as:

> Turning manual, people-dependent operations into small, usable internal systems.

### This means the page should emphasize:

- spreadsheet / Slack / email-driven operations
- admin tools
- internal workflow structure
- backend logic with operational stability
- small scoped MVPs that can actually be used

### And it should de-emphasize:

- broad “I build anything” messaging
- generic web-freelancer positioning
- overly wide service claims
- portfolio-first framing without buyer relevance

## 6) Content blocks to add in Phase 1

### A. Engagement model block

This should answer quickly:

- `Typical timeline`
- `Deliverables`
- `Communication`
- `Scope handling`

Recommended content direction:

- **Typical timeline**
  - Usually best fit for small, scoped projects in the `2–6 week` range.
- **Deliverables**
  - Working MVP / scoped implementation
  - Core backend or workflow logic
  - Optional admin/internal UI
  - Handoff notes / next-step recommendations
- **Communication**
  - Email / document-first
  - Intermediate updates via text, screenshots, short demo clips
  - Short calls only when necessary
- **Scope handling**
  - Start with a clearly limited first scope
  - New requests are split into the next step instead of expanding endlessly mid-stream

> Note: Do **not** publish hard pricing yet unless inquiry volume and offer boundaries become stable enough.  
> A public budget band can be added later if needed.

---

### B. Contact form block

Recommended fields:

- Name
- Email
- What are you trying to improve?
- Project type
  - Internal tool
  - Workflow automation
  - Backend MVP
  - Not sure yet
- Target timeline
- Budget range (optional, can remain internal for now)

Recommended guidance copy:

- `지금 어떤 업무가 수작업인지`
- `누가 그 업무를 하고 있는지`
- `가장 큰 병목 1개`
- `원하는 결과 1개`
- `대략적인 일정`

Keep email as fallback under the form.

---

### C. FAQ block

Recommended FAQ topics:

1. Can I reach out even if my scope is not fully defined yet?
2. Do you accept small projects?
3. How much meeting time is usually needed?
4. What stack do you usually work with?
5. What support is available after handoff?
6. How do you handle IP / ownership?
7. Can you work with sensitive operational data?

---

### D. Featured case rewrite

At least one flagship proof block should be rewritten in this structure:

- **Baseline**
  - what was manual / fragmented / slow
- **What changed**
  - what system / workflow / backend structure was built
- **Result**
  - what became faster, clearer, more repeatable, or more stable
- **Good fit**
  - what kind of team this pattern applies to

This should be prioritized over adding more screenshots.

## 8) Execution roadmap

### Phase 1 — Conversion foundation

Goal: remove the biggest inquiry blockers.

- Rewrite hero for sharper positioning
- Add engagement model block
- Add short intake form + success state
- Add FAQ section
- Rewrite one featured case into `baseline -> change -> result`
- Sharpen ICP wording

### Phase 2 — Trust upgrade

Goal: improve buyer confidence and qualification.

- Add context to metrics
- Rewrite supporting proof cards into `challenge -> built -> impact`
- Add package framing with typical timeline and deliverables
- Add light risk-reduction policy
- Improve “who this is not for” filtering

### Phase 3 — Optimization

Goal: improve performance based on actual usage data.

- Add analytics tracking
- Measure CTA click-through / form-start / form-submit
- Tune section order using scroll-drop behavior
- Consider A/B testing only after meaningful traffic exists
- Consider public budget framing only after enough inquiry data is collected

---

## 9) KPI targets

Track before / after for 2–4 weeks once Phase 1 is shipped.

### Primary metrics

- Hero CTA click-through rate
- Contact start rate (`form open or email click`)
- Contact completion rate (`form submit`)
- Qualified lead rate (`inbound matching actual service scope`)

### Suggested early targets

- `+20–35%` contact-start rate
- `+10–20%` qualified lead rate

> These are directional targets, not guarantees.  
> They should be used as operating benchmarks rather than promises.

---

## 10) Minimum viable next step

If only one first-round implementation pass is possible, do these first:

1. Add a short contact form (`not mail-only`)
2. Add engagement model summary (`timeline / deliverables / communication / scope`)
3. Add FAQ for top objections
4. Sharpen hero messaging
5. Rewrite one flagship case into `baseline -> change -> result`

This set should create the fastest practical conversion lift without requiring a full redesign.

---

## 11) Final operating principle

This page should be improved as a **sales asset**, not just polished as a portfolio page.

The first-round goal is not:

- more design
- more screenshots
- more services
- more technical detail

The first-round goal is:

- clearer positioning
- lower inquiry friction
- stronger trust
- better qualification
- easier decision-making for the right client
